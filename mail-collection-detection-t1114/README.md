Детект чтения локальных почтовых хранилищ (`.pst`, `.ost`, `.nst`) посторонним процессом на основе событий Windows Security 4663.

## 1. Разбор техники

### Как и зачем используется

Техника T1114.001 — сбор почты, которая хранится на самой машине жертвы. Атакующему не нужны пароль от почты или доступ к серверу: достаточно прочитать или скопировать файлы почтового клиента, затем заархивировать и вынести их. Примеры из ATT&CK:

- **APT1** — использовала утилиты GETMAIL и MAPIGET для сбора почты пользователей.
- **Emotet** — применяла модуль, который собирает данные почты из Outlook.

(Актуальные формулировки смотрите на странице техники в ATT&CK.)

Где почтовые клиенты хранят данные:

| Клиент | Путь |
|---|---|
| Outlook, кэш аккаунта | `%LOCALAPPDATA%\Microsoft\Outlook\*.ost` |
| Outlook, архивы | `%USERPROFILE%\Documents\Outlook Files\*.pst` |
| Thunderbird | `%APPDATA%\Thunderbird\Profiles\*\Mail\`, `ImapMail\` |
| Новый Outlook | `%LOCALAPPDATA%\Packages\Microsoft.OutlookForWindows_8wekyb3d8bbwe\` |

### Что нужно, чтобы увидеть чтение файла

Создание и изменение файла видно в Sysmon (EID 11) и обычных журналах. **Чтение** видит только аудит файловой системы Windows: событие Security **4663** появляется, если включена подкатегория *File System* и на объекте стоит SACL с аудитом нужной операции (см. раздел 2).

### Эмуляция на стенде

Реальных пользовательских данных нет, файлы-приманки созданы командами:

```powershell
$u = $env:USERPROFILE
New-Item "$u\Documents\Outlook Files" -ItemType Directory -Force
New-Item "$env:LOCALAPPDATA\Microsoft\Outlook" -ItemType Directory -Force
fsutil file createnew "$u\Documents\Outlook Files\archive.pst" 20971520
fsutil file createnew "$u\Documents\Outlook Files\backup2024.pst" 10485760
fsutil file createnew "$env:LOCALAPPDATA\Microsoft\Outlook\user@corp.local.ost" 31457280
```

Тесты Atomic Red Team для T1114.001 выполнить не удалось: `Get-Inbox.ps1` обращается к COM-объекту `outlook.application`, а на ВМ нет классического Outlook (ошибка `REGDB_E_CLASSNOTREG`; в Windows 11 только новый Outlook, у которого такого COM-интерфейса нет). Использован собственный сценарий [`emulation/emulate_t1114_001.ps1`](emulation/emulate_t1114_001.ps1), он повторяет типичные действия злоумышленника:

1. находит `*.pst` и `*.ost` в профиле пользователя (`Get-ChildItem -Recurse -Force`);
2. копирует их в промежуточный каталог `%TEMP%\stage` (staging);
3. открывает исходные файлы на чтение и читает их;
4. архивирует копии в `%TEMP%\mail.zip` (подготовка к выгрузке);
5. держит хэндлы открытыми 60 секунд, чтобы их можно было увидеть в System Informer.

*Особенность скрипта:* поиск идёт по всему профилю и не исключает `Temp\stage`, поэтому при повторном запуске он находит собственные копии. В прогоне, давшем события для тестов, это привело к ошибкам «Cannot overwrite the item … with itself», а `Compress-Archive` завершился ошибкой «файл используется другим процессом». Для детектирования это не важно: чтение исходных файлов и создание копий прошли успешно (см. 4663 и Sysmon EID 11 ниже).

### Что видно в Procmon и System Informer

**Procmon** (фильтр: `Path contains .pst` / `.ost`, операции `CreateFile` и `ReadFile`). Процесс `powershell.exe` (PID 9008) открывает `user@corp.local.ost`, `archive.pst`, `backup2024.pst` на чтение, затем идёт серия `ReadFile` блоками по 1 МБ (это копирование) и создание копий в `Temp\stage`. Строки `NAME NOT FOUND` на путях в `Temp\stage` — проверка существования перед созданием копии.

![Procmon: CreateFile и ReadFile по .pst/.ost](mail-collection-detection-t1114/screenshots/procmon_pst_ost.png)

**System Informer** (процесс `powershell.exe`, вкладка Handles). Пока скрипт держит файлы, видны хэндлы на оба `.pst` и на `.ost` с правом Read (в списке также хэндлы на копии из `Temp\stage`).

## 2. Настройка сбора событий

Все настройки воспроизводимы скриптами из [`audit/`](audit/). Запускать от администратора:

```powershell
Set-ExecutionPolicy -Scope Process Bypass -Force
```

### 2.1. Политика аудита

Скрипт: [`audit/set-audit-policy.ps1`](audit/set-audit-policy.ps1). Используются GUID подкатегорий, а не имена, поэтому скрипт работает в любой языковой версии Windows.

| Подкатегория | Что даёт | Нужно правилу? |
|---|---|---|
| **File System** | **4663** — попытка доступа к объекту | **да, основное событие** |
| Handle Manipulation | 4656 (запрос хэндла), 4658 (закрытие), 4690 (копирование хэндла) | нет (см. шум ниже) |
| Process Creation | 4688 — создание процесса | нет, контекст при расследовании |

Дополнительно:

- командная строка процесса в 4688: `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\Audit` → `ProcessCreationIncludeCmdLine_Enabled = 1`;
- `SCENoApplyLegacyAuditPolicy = 1`, чтобы настройки подкатегорий не перекрывались старой политикой по категориям;
- размер журнала Security 1 ГБ, чтобы он не перезаписывался во время экспериментов.

Эквивалент в GPO: `Конфигурация компьютера → Конфигурация Windows → Параметры безопасности → Расширенная конфигурация политики аудита → Аудит системы → Доступ к объектам` (*File System*, *Handle Manipulation*) и `Подробное отслеживание` (*Process Creation*).

> Окно `gpedit.msc` показывает «Не настроено», потому что `auditpol` меняет действующую политику напрямую, а не локальную групповую политику. Проверять результат нужно командой `auditpol /get`.

### 2.2. Аудит доступа к объектам (SACL)

Скрипт: [`audit/set-mail-sacl.ps1`](audit/set-mail-sacl.ps1).

| Что | Для кого | Какие операции |
|---|---|---|
| Каталоги `Documents\Outlook Files`, `%LOCALAPPDATA%\Microsoft\Outlook`, `%APPDATA%\Thunderbird\Profiles` (с наследованием) и сами файлы `.pst`/`.ost`/`.nst` | `Everyone` (неизвестно, под какой учёткой работает атакующий) | только **ReadData**, только **Success** |

Почему так:

- только чтение: при аудите записи Outlook засыпает журнал событиями записи в `.ost`;
- только успешные: неудачные обращения для этой задачи — шум;
- SACL ставится и на каталоги, и на сами файлы: правило каталога не доходит до файлов, созданных раньше (см. 2.4).

**Проверка применения** — [`audit/verify-audit.ps1`](audit/verify-audit.ps1): проверяет подкатегории аудита, реестр, размер журнала, SACL на каталогах и файлах, затем делает живой тест (читает файл и ищет событие 4663) и выводит таблицу PASS/FAIL.

![verify-audit.ps1: все проверки пройдены](mail-collection-detection-t1114/screenshots/verify_audit.png)

Пример события после настройки: чтение `backup2024.pst` процессом `powershell.exe`, `Accesses: ReadData`, `Access Mask: 0x1`.

![Событие 4663 в «Просмотре событий»](mail-collection-detection-t1114/screenshots/eventviewer_4663.png)

#### Оценка шума

Замер выполнен скриптом [`audit/count-noise.ps1`](audit/count-noise.ps1) в двух режимах по **30 минут** на каждый (значение «в час» — пересчёт). Результаты: [`audit/noise/`](audit/noise/).

| Режим | Окно (время ВМ) | Событий 4663 | В час | Из них на `.pst/.ost` |
|---|---|---|---|---|
| Простой (машина не используется) | 10:41–11:11 | **0** | 0 | 0 |
| Активный пользователь (Проводник, сканирование Defender, мои собственные проверки) | 11:14–11:44 | **14** | 28 | 3 (6 в час) |

Кто породил 14 событий в активном режиме:

| Процесс | Событий | На что |
|---|---|---|
| `explorer.exe` | 6 | открытие каталога `Outlook Files` (каталог, не файл) |
| `powershell.exe` | 5 | мои проверки: `verify-audit.ps1` (живой тест на `archive.pst`, 1 событие на файл) и обращения к каталогу |
| `MsMpEng.exe` (Defender) | 3 | сканирование: чтение `archive.pst`, `backup2024.pst` и каталога |

Маска доступа во всех событиях `0x1`. Файл `.ost` в окне никто не читал.

![Замер шума: простой](mail-collection-detection-t1114/screenshots/noise_idle.png)

![Замер шума: активный пользователь](mail-collection-detection-t1114/screenshots/noise_active.png)

**Весь журнал Security за те же окна** (по типам событий; `Get-WinEvent ... | Group-Object Id`):

| Событие | Простой, 30 мин | Активный, 30 мин |
|---|---|---|
| 4658 (закрытие хэндла) | 1034 | 49 |
| 4656 (запрос хэндла) | 507 | 25 |
| 4690 (копирование хэндла) | 507 | 25 |
| 4688 (создание процесса) | 39 | 78 |
| **4663 (доступ к объекту, нужен правилу)** | **0** | **14** |
| Всего (по перечисленным типам) | 2127 | 203 |

Подкатегория *Handle Manipulation* (4656/4658/4690) даёт **96% журнала в простое** и около 49% при активной работе, а нужные правилу 4663 — от 0 до 7%. Что именно порождает такой поток 4656/4658/4690 в простое, выяснено не было: для правила эти события не нужны.

**Как снизить шум:**

1. Отключить подкатегорию *Handle Manipulation*. Правилу достаточно 4663, в нём есть и объект, и процесс, и маска доступа.
2. Ограничить SACL операцией ReadData и только почтовыми каталогами и файлами (сделано).
3. Не аудировать неудачные попытки (сделано).
4. Отсекать события на каталоги (без расширения `.pst/.ost`) условием в правиле (сделано, см. раздел 4).
5. Фильтровать известные процессы (Outlook, Defender, Windows Search) в правиле (сделано).
6. В проде: собирать только 4663 по нужным путям через Windows Event Forwarding или фильтр на коллекторе.

### 2.3. Sysmon

Файлы: [`sysmon/sysmon-config.xml`](sysmon/sysmon-config.xml), [`sysmon/config.diff`](sysmon/config.diff), оригинал в [`sysmon/orig-config/`](sysmon/orig-config/). За основу взят публичный конфиг SwiftOnSecurity, в блок `FileCreate onmatch="include"` добавлены три правила:

```diff
 <FileCreate onmatch="include">
+    <TargetFilename name="mail-archive-created" condition="end with">.pst</TargetFilename>
+    <TargetFilename name="mail-cache-created"   condition="end with">.ost</TargetFilename>
+    <TargetFilename name="mail-mbox-created"    condition="end with">.mbox</TargetFilename>
     <TargetFilename name="T1023" condition="contains">\Start Menu</TargetFilename>
```

Что это даёт: Sysmon EID 11 фиксирует **создание** файлов `.pst/.ost/.mbox`, то есть ловит промежуточное копирование почты (staging). В журнале эмуляции ([`events/attack_sysmon.evtx`](events/attack_sysmon.evtx)) три такие записи в 10:14:17 UTC, процесс `powershell.exe`:

| Sysmon EID | Время (UTC) | Процесс | TargetFilename |
|---|---|---|---|
| 11 | 10:14:17 | `powershell.exe` | `C:\Users\admin\AppData\Local\Temp\stage\user@corp.local.ost` |
| 11 | 10:14:17 | `powershell.exe` | `C:\Users\admin\AppData\Local\Temp\stage\archive.pst` |
| 11 | 10:14:17 | `powershell.exe` | `C:\Users\admin\AppData\Local\Temp\stage\backup2024.pst` |

**Sysmon здесь помогает лишь частично.** Он не логирует чтение файла: EID 11 срабатывает только на создание или перезапись, а EID 1 показывает запуск процесса, но не то, какие файлы он затем читает. Поэтому для самого факта чтения (то, из чего состоит техника) нужен аудит Windows (4663), и правило построено на нём. Sysmon годится для обогащения (родитель, командная строка, хэш процесса) и для детекта копирования архивов, это вынесено в планы улучшения правила.

### 2.4. Если событий нет

В процессе настройки несколько раз была ситуация «в Procmon есть, в журнале нет»:

1. **4663 не появлялись, хотя подкатегория File System была включена.** Причина: на папке с почтой не было SACL. Политика только разрешает аудит, а *что именно* аудировать, задаёт SACL. Исправление: [`audit/set-mail-sacl.ps1`](audit/set-mail-sacl.ps1), проверка `Get-Acl ... -Audit`.
2. **SACL на каталоге не доходит до уже существующих файлов.** Правило, поставленное на папку, не подхватилось файлами, созданными раньше. Поэтому скрипт ставит SACL ещё и на каждый `.pst/.ost/.nst` внутри каталога.
3. **События были на `.pst`, но не на `.ost`.** Скрипт эмуляции не заходил в скрытую папку `AppData` (`Get-ChildItem` без `-Force`) и на каталоге с `.ost` не было SACL. Исправлено добавлением `-Force` и SACL.
4. **События на каталог вместо файла.** Собственные проверки (`Get-Acl`, `Get-ChildItem`) и открытие папки в Проводнике создают 4663 на `Outlook Files` (`ListDirectory`). Правило поэтому требует расширение файла в пути объекта.
5. **Atomic Red Team не отработал** (нет COM-класса Outlook), заменён собственным скриптом (см. раздел 1).

Другие причины, которые стоит иметь в виду: нет SACL на конкретном файле; повторные чтения по уже открытому хэндлу событий не дают (4663 создаётся при открытии); чтение через теневую копию (VSS) или напрямую с диска вообще не проходит через SACL.

## 3. Выгрузка событий со стенда

Журналы Windows лежат в `C:\Windows\System32\winevt\Logs\`, но напрямую скопировать их нельзя (файлы держит служба журнала событий). Выгрузка выполнена через «Просмотр событий»:

1. Журналы Windows → **Security** (и *Журналы приложений и служб → Microsoft → Windows → Sysmon → Operational*) → «Фильтр текущего журнала» → «За период времени» → интервал эмуляции.
2. «Сохранить отфильтрованный журнал в файл…» → `.evtx`.

| Файл | Что внутри | Событий | Интервал (UTC), 30.10.2026 |
|---|---|---|---|
| `events/attack_security.evtx` | Security: эмуляция атаки | 422 | 10:12:24 – 10:15:56 |
| `events/attack_sysmon.evtx` | Sysmon: эмуляция (включая EID 11 на `Temp\stage`) | 17 | 10:10:05 – 10:19:02 |
| `events/legit_security.evtx` | Security: легитимная активность | 130 | 10:40:01 – 10:45:57 |
| `events/legit_sysmon.evtx` | Sysmon: тот же интервал | 102 | 10:40:01 – 10:45:57 |

В интервале для негативного теста почтовые файлы читает Defender (`MsMpEng.exe`). Сырые события для тестов правила лежат в `rule/tests/` (`raw_events_1.json` — атака, `raw_events_2.json` — легитимная активность).

## 4. Правило корреляции

Правило написано в расширении [eXtraction and Processing](https://github.com/Security-Experts-Community/vscode-xp) (версия 3.21.7) для VS Code. Файлы `.evtx` открыты в расширении и нормализованы штатными формулами из [`open-xp-rules`](https://github.com/Security-Experts-Community/open-xp-rules) с помощью XP Knowledge Base Toolkit версии 28.0.659.

### Нормализация

События нормализуются штатными формулами без доработок. Для 4663 правило использует поля:

| Поле | Содержимое |
|---|---|
| `msgid` | `4663` |
| `object.fullpath` | путь к файлу (**в нижнем регистре**; в 4656 регистр сохраняется, поэтому в правиле путь приводится к нижнему регистру) |
| `datafield5` | маска доступа (`0x1` = ReadData) |
| `subject.process.fullpath` | путь к процессу, который читает файл |
| `subject.account.name` | пользователь |
| `event_src.host` | хост |

**Ненормализованные события** ([`events/normalized/`](events/normalized/)):

| Журнал | Не нормализовано | Какие события |
|---|---|---|
| `attack_security.evtx` | 203 из 422 | только 4658 (закрытие хэндла) |
| `legit_security.evtx` | 24 из 130 | 4658 (14), 5379 (6), 5058 (2), 5061 (2) |

Для 4658 в открытом наборе нет формулы нормализации. Это не мешает: правило работает на 4663, и они нормализованы (в позитивном тесте срабатывает 6 раз). Дорабатывать нормализацию не потребовалось.

### Логика правила

Файл: [`rule/rule.co`](rule/rule.co).

Что делает каждое условие:

| Условие | Зачем |
|---|---|
| `msgid == "4663"` | доступ к объекту; единственное событие, где видно чтение |
| `regex(lower(object.fullpath), "[.](pst\|ost\|nst)$")` | только почтовые файлы; отсекает 4663 на каталоги (папка `Outlook Files` без расширения) |
| `datafield5 == "0x1"` | именно право ReadData (SACL аудирует только чтение) |
| белый список (отрицание) | не срабатывать на штатных потребителях почтовых файлов |
| `filter::NotFromCorrelator()` | не обрабатывать события, порождённые самими правилами |
| `key: event_src.host` | корреляция в пределах одного хоста |
| `incident.aggregation.key` = правило + хост + процесс, таймаут 10 минут | массовое чтение одним процессом даёт один инцидент, а не десятки |

**Белый список процессов** (сравнение по полному пути без учёта регистра, а не по имени: иначе его можно обойти, назвав файл `outlook.exe`):

| Процесс | Почему в списке |
|---|---|
| `C:\Program Files\Microsoft Office\...\OUTLOOK.EXE` | основной потребитель `.pst/.ost` |
| `C:\Program Files\WindowsApps\Microsoft.OutlookForWindows_...\olk.exe` | новый Outlook |
| `C:\ProgramData\Microsoft\Windows Defender\Platform\...\MsMpEng.exe` | антивирус сканирует файлы (в замере шума читал `.pst`) |
| `C:\Windows\System32\SearchProtocolHost.exe`, `SearchIndexer.exe` | индексатор Windows Search |

В замере шума ни одного другого процесса, читавшего почтовые файлы, кроме Defender и моих собственных проверок, не оказалось; это означает, что для этой ВМ список достаточен, но на реальных машинах его придётся дополнять.

### Какие легитимные программы делают то же самое

Читают почтовые хранилища в обычной работе: Outlook и Thunderbird, индексатор Windows Search, антивирус и EDR (Defender и сторонние), агенты резервного копирования и теневого копирования, DLP-системы, утилиты миграции почты, `scanpst.exe` (восстановление `.pst`), синхронизаторы облачных хранилищ (OneDrive), ручное копирование `.pst` пользователем. Часть из них учтена в белом списке, остальные — потенциальные ложные срабатывания, их нужно добавлять в белый список по результатам эксплуатации.

### Метаданные и описание

- [`rule/metainfo.yaml`](rule/metainfo.yaml): техника T1114.001 (тактика Collection), источник данных (Microsoft-Windows-Security-Auditing, EID 4663), сценарии использования, улучшения.
- [`rule/i18n/i18n_ru.yaml`](rule/i18n/i18n_ru.yaml) и [`i18n_en.yaml`](rule/i18n/i18n_en.yaml): описание правила, возможные ложные срабатывания, текст инцидента с подстановкой хоста, процесса, пользователя и файла.

## 6. Самооценка

### Как злоумышленник может обойти правило

| Способ обхода | Закрыто? |
|---|---|
| Чтение через сам Outlook (COM/MAPI-автоматизация, как в `Get-Inbox.ps1` из Atomic Red Team): файл читает `outlook.exe`, он в белом списке | **нет**. Нужна поведенческая связка (необычный родитель Outlook, скрипт, поднимающий Outlook через COM) |
| Внедрение кода в процесс из белого списка (Outlook, Defender) | **нет** |
| Чтение через теневую копию (VSS) или напрямую с диска | **нет**: SACL не срабатывает |
| Копирование файла в каталог без SACL и дальнейшая работа с копией | **частично**: копирование читает исходник и даёт 4663, но чтение уже готовой копии вне каталогов с SACL событий не создаёт |
| Положить свой исполняемый файл под путь из белого списка | **закрыто в части переименования** (сравнение по полному пути); для подмены пути нужны права администратора |
| Файлы `.pst/.ost` в нестандартном каталоге без SACL | **нет**: аудит стоит только на типовых каталогах |
| Другие клиенты (Thunderbird `mbox` без расширения, новый Outlook) | **нет**: правило ловит только `.pst/.ost/.nst` |
| Очистка журнала Security или отключение аудита | **нет** (нужна отдельная детекция: 1102, 4719) |
| Чтение с другой маской доступа (не `0x1`) | **частично**: проверка строгая, но SACL аудирует только ReadData |

### Что было бы сделано ещё за неделю

1. Добавила порог по числу разных почтовых файлов, прочитанных одним процессом за короткое время.
2. Связала чтение с последующей архивацией (Sysmon EID 11: копии `.pst/.ost` вне профиля Outlook) и с исходящим сетевым соединением (Sysmon EID 3).
3. Обогатила инцидент данными о процессе (Sysmon EID 1: родитель, командная строка, хэш) и перешла бы с сравнения по пути на проверку цифровой подписи.
4. Расширила правило на Thunderbird (`Mail`, `ImapMail`) и новый Outlook.
5. Расширила набор негативных тестов реальной легитимной активностью: агенты резервного копирования, индексатор Windows Search, сторонний антивирус, миграция почты.
6. Повторила замер шума на более длинном окне (сутки) и на нескольких машинах, а не 30 минут на одной; выяснила бы, что порождает поток событий Handle Manipulation в простое.

## Как воспроизвести

1. ВМ Windows 11; установить Sysmon с `sysmon/sysmon-config.xml`, Procmon и System Informer.
2. `audit/set-audit-policy.ps1`, затем создать файлы-приманки (раздел 1) и запустить `audit/set-mail-sacl.ps1`; проверить `audit/verify-audit.ps1` (ожидается `ALL CHECKS PASSED`).
3. Запустить `emulation/emulate_t1114_001.ps1`, наблюдать в Procmon и System Informer.
4. Выгрузить журналы Security и Sysmon за интервал эмуляции и за интервал легитимной активности (раздел 3).
5. В VS Code с расширением XP открыть `open-xp-rules`, указать путь к KBT в настройке `Xp Config: Kbt Base Directory`, выполнить *Normalize Events from Files* для `.evtx`, прогнать интеграционные тесты правила `Local_Email_Collection`.
